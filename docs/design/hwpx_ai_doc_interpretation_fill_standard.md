# HWPX AI 문서 해석·자동채움 기준서 (v1)

**제정**: 2026-08-01
**근거**: 같은 날 전수 조사 실측 (아래 §2)
**지시**: 대표님 — "기준서를 먼저 작성하고 드라이 런 진행을 운영규칙에
반영하고 모듈화 처리해"

---

## 1. 목적과 범위

AI가 서식 문서를 **해석**해서 "어느 칸(paragraphId)에 무엇을 넣을지"
결정하는 공정의 기준을 정한다.

- **포함**: 문서 문맥 추출 → AI 해석(값 후보 결정) → 검증 → 드라이 런
  보고. 여기까지가 이 기준서의 공정이다.
- **제외**: 실제 기입(쓰기)은 기존 공정(`form_direct_fill` /
  `para_save_apply`)을 그대로 쓴다 — 전수 검증 완료된 배관을 재발명하지
  않는다. 브라우저 패널 연결(UI)은 별도 공정.

## 2. 실측 근거 (2026-08-01 전수 조사)

| 항목 | 실측값 |
|------|--------|
| 기입(쓰기) 전수 | 31,408서식 · 370,505칸 중 실패 0.07% — 전부 낡은 스키마 3건 소속 |
| 실기입 e2e | 305서식 + 패널 경로 63서식 = 오배치 0 · 유출 0 |
| 신청인칸 의미태그(semantic) 보유율 | 35.0% (179,404칸 중) |
| AI 라벨-단독 매핑률 (현행 ai_form_fill) | **30.7%** (101칸 중 31) — 이 기준서의 개선 대상 기준선 |
| 라벨 오염 | 헤더/체크박스형 6,653 + 30자 초과 3,007 |

결론: 병목은 쓰기가 아니라 **해석**이다. 현행 AI 호출은 라벨 문자열만
받고 문서를 보지 못한다. 로드 시 "AI 필드 인식"은 규칙 기반이라 AI 가
아니다.

## 3. 공정 원칙 (안전선 — CLAUDE.md 계승)

1. **값 비창조(非創造)**: AI 는 값을 만들지 않는다. 제안값은 반드시
   소스 데이터(사용자 제공 프로필/추출값)에서 유래해야 하며, 소스에서
   유래를 입증 못 하는 제안은 검증기가 **기계적으로 폐기**한다
   (`NON_SOURCE_VALUE`). 관공서 제출물에 그럴듯한 값을 지어 넣으면 허위
   기재다.
2. **제3자 칸 보호**: 라벨 기준 서버 판정(`partition_by_subject`)으로
   제3자 칸은 AI 에게 라벨조차 보내지 않는다 — 기존 규칙 그대로.
3. **민감칸**: 제안은 하되 자동 확정 금지(`requiresConfirmation`) — 기존
   규칙 그대로.
4. **AI 경로**: §7/§9 — Claude Code CLI, 모델은 Haiku(최하위) 고정.
   모델 등급 상향은 문맥 제공 후 실측치를 보고 대표님이 별도 결정한다.
5. **원본 무수정**: 이 공정은 어떤 단계에서도 HWPX 를 쓰지 않는다
   (드라이 런 = 무기입). 실기입은 기존 공정의 게이트(§4.3/§4.4)를 따른다.
6. **개인정보**: 소스 데이터는 요청이 실어 보내고 서버에 저장하지
   않는다 — 기존 fill-plan 원칙 그대로. 드라이 런 보고에는 민감값을
   마스킹해 기록한다.

## 4. 드라이 런 의무 (운영규칙 — CLAUDE.md §4.5 로 반영)

**AI 해석·자동채움은 드라이 런을 선행하지 않으면 기입 단계로 넘어갈 수
없다.**

- 드라이 런 = 해석→검증까지만 수행하고 **기입은 하지 않는** 실행. 산출은
  보고서(JSON)뿐이다.
- 드라이 런 보고서 필수 항목: 서식 식별자 · 제안 목록(칸·값·근거
  소스필드·confidence) · 검증 결과(폐기 사유 포함) · 게이트 판정.
- 기입 허용 조건: 드라이 런 게이트 **PASS** 인 제안만, 그리고 민감칸은
  사람 확인 후에만.
- 게이트 판정 기준:
  - `NON_SOURCE_VALUE` 폐기 후 잔존 제안만 통과 (비창조 위반 통과 0건)
  - 제안 대상 paragraphId 전량이 실파일에서 주소 해석 가능
    (`ADDRESS_UNRESOLVED` 0건 — 낡은 스키마 방어)
  - 제3자 칸 제안 0건

## 5. 모듈 구조 (모듈화 기준)

단일 책임으로 4모듈로 나눈다. AI(비결정적·외부 프로세스)는 한 모듈에만
격리하고, 나머지는 순수 함수로 만들어 시험 가능하게 한다.

| 모듈 | 책임 | 성격 |
|------|------|------|
| `ai_doc_context.py` | 문서 문맥 추출 — 입력칸별 행/열 머리글·이웃 셀 텍스트·서식 제목 | 순수 (AI 무관) |
| `ai_doc_interpret.py` | 문맥 포함 프롬프트 구성 · CLI 호출 · 응답 파싱 | AI 경계 (runner 주입 가능) |
| `ai_fill_validate.py` | 비창조 검증 · 민감칸 플래그 · 주소 해석 검증 | 순수 + 파일 읽기 |
| `ai_fill_dry_run.py` | 오케스트레이터 — 로드→문맥→해석→검증→보고서. **기입 없음** | 조립만 |

재사용(§11-6 자재 재사용 원칙):
- 제3자 분리 `ai_form_fill.partition_by_subject`, JSON 파싱
  `_parse_json_array` — 기존 모듈 그대로 임포트.
- 주소 해석 규칙 — `form_direct_fill` 의 프로덕션 함수
  (`parse_paragraph_id` 등)를 그대로 임포트. 재구현 금지(전수 조사도
  같은 방식으로 검증했다).
- 로드/파싱 캐시 — `editor_file_bridge.load_hwpx_for_editor`.

`ai_doc_interpret` 는 `runner`(프롬프트→응답 문자열 함수)를 주입받는다.
기본값은 Claude CLI, 시험에서는 가짜 runner — CLI 없이 전 모듈이
시험된다.

## 6. 게이트 (수치 기준)

- 회귀: 관련 pytest 전량 PASS (신규 모듈 시험 포함).
- 실측: 표본 드라이 런에서 기준선 **30.7%**(라벨 단독) 대비 매핑률 향상
  실측 기록. 수치는 커밋 메시지/보고에 남긴다.
- 비창조 위반 통과 0건 · 제3자 칸 제안 0건 · 주소 해석 실패 통과 0건.
- 이 공정은 HWPX 를 쓰지 않으므로 한컴 열림 게이트는 해당 없음(실기입
  공정의 기존 게이트가 담당).

## 7. 이후 공정 (이 기준서 범위 밖, 착수 시 별도 계획)

- 브라우저 질문 패널에 드라이 런 보고서 표시 + 사람 확인 → 기입 연결.
- 라벨 정제(헤더/안내문 오염 제거) — 스키마 재생성 동반.
- 낡은 스키마 3건 재생성 + 카탈로그 sha 기록·대조 게이트.
- `RUN_TEXT_NODE_MISSING` 수리(runs[0] → 첫 텍스트 run).
