# Web Office Backend Structure Standard

Date: 2026-05-25
Status: ACTIVE STANDARD
Task: WEB-OFFICE-BACKEND-STRUCTURE-STANDARD-53

## 1. Purpose

This standard freezes the current Web Office backend structure for the browser
editor line. It defines the allowed API surface, frontend/backend boundary,
static serving boundary, security rules, and validation commands for the current
sandbox-only implementation.

This standard is not production rollout approval.

## 2. Current Scope

The current Web Office editor line consists of:

- backend API route: `scripts/hwpx/web_office/editor_api_route.py`
- backend load bridge: `scripts/hwpx/web_office/editor_file_bridge.py`
- backend save bridge: `scripts/hwpx/web_office/save_apply_bridge.py`
- frontend API bridge: `frontend/web_office_viewer/real_file_load_save_bridge.mjs`
- frontend save bridge: `frontend/web_office_viewer/save_apply_bridge.mjs`
- frontend UI controller: `frontend/web_office_viewer/editor_ui_bridge.mjs`
- static editor shell: `frontend/web_office_viewer/index.html`
- browser smoke: `tests/test_web_office_editor_browser_smoke.py`
- backend route tests: `tests/test_web_office_writer_readback_backend_api_route.py`
- frontend/backend wire tests: `tests/test_web_office_browser_smoke_frontend_backend_wire_baseline.py`
- current app structure map: `docs/architecture/web_office_app_structure_20260525.md`

## 3. Allowed Runtime Mode

The only approved runtime mode is:

- `SANDBOX_ONLY`

All public API envelopes must keep:

- `sourceMutationAllowed == false`
- no production write capability
- no source overwrite capability
- no direct final deploy capability

## 4. Backend API Surface

The backend API surface is limited to:

- `GET /api/web-office/health`
- `POST /api/web-office/hwpx-load`
- `POST /api/web-office/cell-save-apply`

The health response must expose the active load and save endpoints and confirm
that the pipeline is ready without exposing local filesystem locations.

The load endpoint accepts project-relative safe fixture paths only. It must
reject absolute paths and unsupported source path forms.

The save endpoint accepts a browser command log and writes only to sandbox output
location configured by the backend runtime. The public response must not expose
the internal output path.

## 5. Static Frontend Serving

The backend may serve the browser editor at:

- `GET /web-office/`
- `GET /web-office/*`

Static serving is limited to:

- `frontend/web_office_viewer`

The static route must not serve files outside that frontend directory. Static
serving must not change the API route contracts.

## 6. Frontend Boundary

The browser frontend may:

- call `POST /api/web-office/hwpx-load`
- call `POST /api/web-office/cell-save-apply`
- unwrap backend response envelopes
- build editor state from `data.documentModel`
- create browser-side `SET_CELL_TEXT` commands
- keep a browser-side append-only command log
- render success, blocked, fail, and loading states

The browser frontend must not:

- parse HWPX packages directly
- write HWPX files directly
- choose local output paths
- call backend writer modules directly
- expose absolute local paths
- expose raw file names
- expose PII
- show failed or blocked saves as success

## 7. Save Contract

The browser save request must include:

- `operation`
- `sourcePath`
- `sourceDocumentHash`
- `commandLog`

The command log must be generated by browser-side editor state, but file writing
and readback verification remain backend responsibilities.

Save success is valid only when the backend reports a passing save result and
the public response hides internal output path details.

## 8. Failure State Contract

The UI must distinguish:

- load HTTP failure: `fail`
- save HTTP failure: `fail`
- save validation rejection or non-pass verdict: `blocked`
- successful backend save apply: `success`

Blocked and failed states must never show the success message.

When a save is blocked or fails, the command log must remain available for user
correction or retry.

## 9. Visual Runtime Contract

The browser editor must render a usable layout in at least:

- desktop viewport
- mobile viewport

The following areas must be visible after loading the sample document:

- title
- load button
- save button
- status bar
- cell list
- inspector panel
- at least one cell

Core document and inspector regions must not overlap incoherently in desktop or
mobile viewports.

## 10. Security Contract

The following leak counters must stay at zero in API responses, DOM text,
console output, and committed reports:

- PII leak
- raw absolute path leak
- raw filename leak

Public API responses must not include `outputPath`.

The backend may use a local sandbox output directory internally, but that path
must not cross the public API boundary.

## 12. Pass Criteria

The implementation passes this standard when:

- health route returns `SUCCESS`
- load route returns `SUCCESS` for the safe project-relative fixture
- load route rejects absolute source paths
- save route returns `SUCCESS` for a valid command log
- backend readback verification passes
- source document remains unchanged
- public save response hides `outputPath`
- frontend bridge uses only fixed backend editor routes
- browser success smoke passes
- browser failure-state smoke passes
- browser visual smoke passes for desktop and mobile
- repo new file classification gate passes
- commit and push guards pass
- verified changes are present on `haehan-app`
- server health check returns `HEALTHY`, or `RECOVERED` followed by `HEALTHY`
- server response keeps `mode == SANDBOX_ONLY`
- server response keeps `sourceMutationAllowed == false`
- server monitor process or `@reboot` auto-start registration is present
- server monitor can include app structure drift audit and reports it as pass
- read-only security log audit can be run on the server without changing
  firewall, IP allowlist, or port policy
- operational report artifact is written with validation command results,
  server verification result, unresolved items, and final status

Local validation alone is not sufficient for Web Office completion. Completion
requires successful server validation.

## 13. Hold Items

The following remain outside this standard:

- production write
- real user upload
- uncontrolled user file selection
- direct browser HWPX package parsing
- direct browser HWPX writing
- deployment or final operational export

Any attempt to enable these requires a new task standard and explicit approval.

## 14. Change Control

Changes to the following require a new task standard:

- API route additions or removals
- static serving scope changes
- save contract changes
- upload/source path policy changes
- production mode changes
- security exception changes
- browser direct file access changes
- firewall, IP allowlist, or port exposure policy changes

This standard should be used as the review checklist for future Web Office
backend and browser editor work.

## 15. Operational Completion Rule

For all future Web Office tasks:

- local development and local tests are pre-deployment checks
- server verification is the final acceptance check
- a task is incomplete until the server baseline passes
- completion reports must state both local validation and server validation

If local validation passes but the server is not checked, the correct status is
`LOCAL_VERIFIED_SERVER_PENDING`.

If server validation fails, the correct status is
`SERVER_VERIFICATION_FAILED`, even if all local checks passed.

## 16. Operational Report Artifact Rule

Every Web Office backend task that changes backend modules, API routes, runtime
scripts, monitoring, recovery, deployment, server state, validation gates, or
backend structure must write a completion report artifact before closeout.

The artifact must be machine-readable when practical, preferably JSON, and must
record:

- `schemaVersion`
- `task`
- `baselineHead`
- `standardDocuments`
- `changedFiles`
- `validationCommands`
- `localVerification`
- `serverVerification`
- `reportArtifacts`
- `unresolvedItems`
- `holdItems`
- `finalStatus`

The report must explicitly state whether the backend standard document was
updated, whether the work result was deployed to `haehan-app`, and whether the
server health, sandbox mode, source mutation block, monitor process, and
monitor auto-start registration passed.

Allowed final status values for Web Office backend work:

- `LOCAL_VERIFIED_SERVER_PENDING`
- `SERVER_VERIFIED_PASS`
- `SERVER_VERIFICATION_FAILED`
- `LOCAL_VERIFICATION_FAILED`
- `DOCUMENTATION_ONLY_RECORDED`

Completion is invalid if:

- validation commands are not recorded
- local verification result is missing
- server verification is required but missing
- unresolved or hold items are omitted
- the final status value is absent
